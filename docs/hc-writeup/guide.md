# 比赛 WP 写作教程

> 面向 HBEU-OSC 成员与社区投稿者。读完这一篇，你应该能独立完成一篇**可复现、可审阅、可发布**的解题报告。
>
> 配套材料：[投稿模板](template.md.txt) · [比赛 WP 列表](../sidebar/writeups.html) · 栏目首页（[hc-writeup/index.md](index.md)）

## 为什么值得写 {#why}

- **复盘**：把"当时怎么想到的"固化下来，下次遇到同类题可以直接复用思路。
- **传承**：新人靠 WP 入门，比只看题库的标答更接近真实比赛过程。
- **表达**：面试、评奖、组队时，一篇结构清晰的 WP 比一句"我做出来过"更有说服力。
- **校验**：写不清楚的段落，往往就是自己没真正搞懂的地方。

## 一篇好 WP 的标准 {#standard}

| 维度 | 合格线 | 加分项 |
| --- | --- | --- |
| 可复现 | 别人按步骤能跑出同样结果 | 环境与依赖版本、一键脚本 |
| 有推理 | 讲清"为什么这么做"，而不只贴结果 | 失败尝试与排除过程 |
| 可读 | 结构清晰、代码可读、截图有标注 | 图示、表格、时间线 |
| 合规 | 无敏感信息、遵守赛规与许可 | 标注引用来源与授权范围 |

## 标准结构 {#structure}

与[投稿模板](template.md.txt)一一对应，建议按顺序写：

1. **题目信息**：比赛、方向、题名、附件、运行环境、关键线索；
2. **解题思路**：从线索到假设，再到验证/排除假设的完整推理链；
3. **分析与复现**：分步骤写，每一步给命令、输出和结论；
4. **核心代码**：最小可复现脚本，注释说明输入、输出和关键逻辑；
5. **结果验证**：如何确认成功（Flag 按比赛规则决定是否展示/脱敏）；
6. **复盘与经验**：关键知识点、踩过的坑、还能怎么改进；
7. **参考资料**：引用的文章、工具文档、他人思路。

> 结构不是八股。简单题可以合并小节，但"思路 → 复现 → 验证"这条主线不要丢。

## 赛前与赛中怎么记录 {#notekeeping}

赛后回忆写 WP 最大的问题是**细节丢失**。建议：

- **开赛前**：先建好 `docs/hc-writeup/<年份>/<比赛名>/` 目录和空文件，把模板粘贴进去；
- **赛中**：每 15–30 分钟对关键界面截一次图；命令用 `script`、`history` 或笔记留存；脚本随手保存；
- **截图规范**：能看清关键行、圈注重点、不要截到 Flag、账号、令牌；
- **时间线**：记下"什么时候想到什么"，这是复盘部分最有价值的内容；
- **赛后 24 小时内**补全正文，记忆最鲜活。

## Front matter 字段说明 {#frontmatter}

列表页由构建钩子 [hooks/generate_writeups.py](https://github.com/dff-ice/HBEU-OSC-CTF/blob/main/hooks/generate_writeups.py) 自动生成，**只认下面这些字段**：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `type` | ✅ | 固定写 `writeup`，**这是被收录的开关**，漏了就不会出现在列表 |
| `title` | ✅ | 列表与页面标题，建议 `比赛 - 方向 - 题目` |
| `date` | ✅ | 发布日期，列表按它倒序排列，格式 `YYYY-MM-DD` |
| `authors` | ✅ | 作者，可写多个（YAML 列表） |
| `competition` | ✅ | 比赛名称，如 `ISCC 2026` |
| `category` | ✅ | 方向，建议只用 `Web / Crypto / Reverse / Pwn / Misc / AWD / AI / Blockchain / Other` |
| `description` | 建议 | 列表摘要，超长会被截断到 220 字 |
| `comments` | 可选 | `true` 时页面底部显示 giscus 评论 |

示例：

```yaml
---
title: "ISCC 2026 - Pwn - combination"
type: writeup
date: 2026-10-26
authors:
  - "杨心凌"
competition: "ISCC 2026"
category: "Pwn"
description: "分析 UAF 与空字节越界，利用堆布局破坏构造任意读写并劫持返回地址。"
comments: true
---
```

> 如果想加 `tags`、`difficulty` 之类的新字段，需要同步修改钩子脚本，否则列表页读不到——这一点请先和负责人确认。

## 目录与命名规范 {#layout}

```
docs/hc-writeup/
└─ 2026/                      ← 年份（4 位）
   └─ ISCC2026/              ← 比赛名（官方名或通用缩写）
      ├─ combination.md       ← 一题一文件
      ├─ conways-trap.md
      └─ assets/              ← 本场比赛的图片与附件
         ├─ combination-files.png
         └─ combination-attachment.zip
```

约定：

- 年份 4 位；比赛名用官方英文名或通用缩写（`ISCC2026`、`CISCN2026`、`NSSCTF`…）；
- 文件名用**英文小写 + 连字符**（`ez-sql.md`）。中文文件名也能构建，但 URL 和锚点更容易出问题，不推荐；
- 同一场比赛的多道题放在同一个比赛目录下；
- 图片、附件放同级 `assets/`，正文用相对路径引用：`![说明](assets/xxx.png)`。

## 附件、图片与代码 {#assets}

| 类型 | 规范 |
| --- | --- |
| 图片 | 优先 `webp`/`png`，单张建议 ≤ 300 KB；命名 `01-题目界面.png`；正文配一句说明 |
| 附件 | 单个文件 ≤ 5 MB 可以直接进仓库；更大的走对象存储/外部链接，并在正文说明来源 |
| 代码 | 标注语言；只贴关键片段；脚本写清运行命令和参数；避免贴大段无关输出 |
| 命令 | 用 `text` 或对应 shell 语言块；写清是否需要 root、依赖版本 |

## 分方向写作要点 {#directions}

- **Web**：请求/响应报文、payload、回显、利用链要能对上；Burp 截图要能看清请求行和参数。
- **Pwn**：保护机制、漏洞点、偏移计算、exp 逐段解释、libc 版本；建议附本地复现命令。
- **Reverse**：关键函数、算法还原过程、动态调试断点位置、patch 前后对比。
- **Crypto**：数学推导、脚本（sage / pycryptodome）、每个参数的含义。
- **Misc**：流量过滤条件、隐写工具与参数、取证步骤顺序。
- **AWD**：攻防节奏、批量脚本、修复思路；注意不要公开对手队伍信息。
- **AI / 区块链**：模型或合约细节、环境版本、复现条件（比赛平台差异要写清楚）。

## 脱敏与合规 {#sanitize}

发布前必须处理：

- 删除或替换：真实 Flag、token、cookie、账号密码、内网/公网地址、他人个人信息；
- **比赛规则**：未允许公开前不发；只对比赛授权的题目环境做复现；
- **引用**：思路来自他人的，注明链接与作者；
- **许可证**：本仓库代码 GPLv3、文档 CC BY-SA 4.0，转载/改编需保留署名与相同方式共享；
- **平台差异**：部分比赛禁止赛后公开原题面，WP 中用"题目要求概述"替代原文。

## 常见错误 {#mistakes}

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 只贴 Flag 和最终脚本 | 别人无法复现，也无法学习 | 补全思路与中间步骤 |
| 截图没有标注 | 读者找不到重点 | 圈注关键行，配文字说明 |
| 路径写死 `C:\Users\...` | 别人跑不了 | 用相对路径或说明变量 |
| 直接复制题面 | 可能违反比赛规则 | 改写成概述，附官方链接（如允许） |
| front matter 漏 `type` | 不进列表页 | 必填 `type: writeup` |
| 图片用绝对路径或中文名 | 构建警告/链接失效 | 相对路径 + 英文文件名 |
| 正文没有验证步骤 | 无法证明思路有效 | 写清如何确认成功 |

## 本地预览与自检 {#preview}

```bash
python -m pip install -r requirements.txt   # 首次
python -m mkdocs serve                      # http://127.0.0.1:8000
python -m mkdocs build                      # 构建到 site/
```

构建成功时日志里会有一行 `Generated WP index: N entries`，N 比之前 +1 说明你的文章被收录了。

## 投稿流程 {#submit}

1. 复制[投稿模板](template.md.txt)，保存为 `.md`；
2. 按上面的目录规范放到 `docs/hc-writeup/<年份>/<比赛名>/`；
3. 图片/附件放同级 `assets/`；
4. 本地 `python -m mkdocs serve` 预览，检查导航、图片、代码块；
5. 提交 Pull Request（标题建议：`WP: <比赛> - <方向> - <题目>`）；
6. 管理员按下面的清单审核，合并后自动部署。

## 审核清单 {#review-checklist}

- [ ] front matter 完整，且 `type: writeup`
- [ ] 目录、文件名符合规范
- [ ] 有题目信息与推理过程，不只是结果
- [ ] 复现步骤完整（环境、命令、参数）
- [ ] 代码可读、注释足够
- [ ] 图片/附件可访问、体积合规
- [ ] 无敏感信息（Flag、令牌、地址、账号）
- [ ] 遵守比赛规则与许可证，引用已注明
- [ ] 本地 `mkdocs build` 通过、无新增 warning
- [ ] 列表页能看到这篇文章

## 进阶建议 {#advanced}

- 给同一场比赛写一篇"总览 + 多题"的导航页，方便按比赛浏览；
- 把可复用的脚本抽出来放进 `resource/`，WP 里引用；
- 赛后写"如果重来一次"的改进版思路，比单纯复述过程更有价值；
- 定期回看旧 WP，补上当时没搞懂的点。
